# REST route generation recurses to the complex property, and we own the generator

The resource middleware's datamodel CRUD API is generated by a **local recursive router**, which
calls `aas_middleware`'s generator for the top-level CRUD and then descends through nested
`Identifiable` models, **terminating at a `PropertyValueKind.COMPLEX` property** whose
blanknode-backed dict is the atomic addressable unit:

```
GET|PUT /{TransferUnit}/{tui:TransferUnit1}
                       /{tu:hasConveyorBelt}/{tui:ConveyorBelt1_left}
                       /{tu:hasConveyorSpeed}
     body: [{ inf:hasValue: 3.0, tu:hasUnit: "m/s", inf:accessMode: "readwrite" }]
```

**Corrected 2026-07-30 (#41), having run it:** the example above showed a bare dict. Every value in
the materialized tree is a **list** — RDF multiplicity, scalars included — which #29's research
established after this ADR was written, so the body is a list of parameter dicts. The decision that
follows: **GET and PUT are symmetric, and PUT accepts exactly what GET returns.** A consumer that
read-modify-writes has to be able to send back what it received, and #43's controller derives its
PUT paths structurally from the GET response and echoes the tree — its acceptance turns on echoing
`accessMode` back unchanged producing no triple write. An asymmetric pair would break that.

## Why

### The framework generator provably cannot reach a parameter

`generate_endpoints_from_model` generates routes for the top-level model and **only its direct
attributes** that are themselves `Identifiable` — no recursion
(`aas_middleware/middleware/rest_routers.py`). A conveyor speed is two levels down *and* lives on a
blanknode, which materializes as an `AnonymousClass` with no `id`
(`kapps_ogm/mapping/class_spec.py`) — not `Identifiable`, therefore never routable.

**Corrected 2026-07-27 (#29), having run it:** this ADR originally stated that the framework
generator yields three addressable things — the unit, the whole list of belts, and the whole list of
barriers. It yields **one**. `get_contained_models_attribute_info` admits an attribute only if its
annotation passes `is_identifiable_type`
(`aas_middleware/model/formatting/aas/aas_middleware_util.py`), and `ClassSpec.to_pydantic_model`
builds every model on plain `pydantic.BaseModel`. Belts and barriers are as invisible to the
generator as the speeds are:

```
GET|PUT|DELETE  /..._TransferUnit/{item_id}      <- the only routes generated
```

The decision is unaffected — the router is ours either way — but #41 starts from **zero** levels of
descent rather than one, and nothing about the nesting can be inherited from the framework.

So "set ConveyorBelt1_left's speed to 3.0" was expressible only as a **read-modify-write of the
entire belt list**: every setpoint re-asserting the sibling belt's speed and the light barriers'
sensor readings, with two controllers clobbering each other. That is a bulk state replacement
masquerading as a control action. **ADR 0015 decided "reads and writes reuse the framework CRUD"
before this limit was known**. This ADR is what that decision looks like once it is.

### The blanknode dict is the right atom, because that pattern is locked

RDF has no properties-about-properties, so metadata *about* a conveyor speed (its unit, its MQTT
topic) is modelled as a blanknode hanging off `tu:hasConveyorSpeed`. That pattern is **locked and
carried across the whole circular factory**, and the OGM already materializes it as one dict via the
complex `PropertySpec`. Treating that dict as the atomic element makes the id-less-`AnonymousClass`
problem disappear rather than solving it: the blanknode never needs a path segment, because the
**property** is the last segment and the dict is the body. Value and unit move together, as they must
— a speed without its unit is not a speed.

### Access mode gates the verb

`inf:accessMode` (ADR 0015's settability facet) is projected into the northbound view (ADR 0018), so
the generator reads it from the same field it serves and emits **no PUT route at all** for a
read-only parameter. A write to a light barrier is a 405 from the server, not a runtime rejection
from a connector — the API advertises only what it will honour. Echoing the facet back on a PUT is
free because `OGM.commit` filters unchanged triples before committing.

**Path segments are literal, not FastAPI path parameters** — one concrete route per individual.
The verb gate is **per individual**: one belt may be `readwrite` while a light barrier on the same
unit is `read`, and a single parameterised route cannot emit PUT for one and withhold it from the
other. Literal segments are what make "no PUT route exists for a read-only parameter" true per
individual rather than per class. The consequence is that the framework's top-level route
parameterises the item (`/{Model}/{item_id}`) while the parameter routes beneath it are literal, so
the two levels encode ids differently — tolerable exactly because a consumer derives the deep paths
from a GET response rather than constructing them, and because `IRI.lined` is total and invertible
(ADR 0021).

### Local, per the dependency policy

Recursion is **new functionality**, and root ADR 0001 is unambiguous: new functionality never goes
into a sibling repo, bugfixes only. It also lands exactly where core ADR 0001 planned to start
paying down the fork — *"replace pieces with local implementations one at a time as they are
understood well enough to own"*. The REST-router layer is now understood well enough to own, so it
becomes the first piece migrated. `aas_middleware_inf` is untouched.

**The local router composes with the framework generator rather than replacing it.** It calls
`generate_rest_api_for_data_model` for the top-level CRUD, then adds the parameter routes beneath
it. The piece that had to be owned locally is **recursion** — that is what the framework provably
cannot do. Re-implementing the top-level CRUD as well would have put "scenarios 1 and 2 still start
and pass" at risk for no gain: those scenarios have no bindings, so they receive exactly the
framework surface they have today. This is the incremental-replacement plan applied literally —
recursion is understood well enough to own. The top-level CRUD is not yet.

## Considered and rejected

- **Whole-list read-modify-write** — honours ADR 0015 literally and needs no new code, but makes a
  setpoint clobber its siblings and read-only sensor values.
- **A bespoke per-parameter route** (`/parameters/{component}/{param}`) generated beside the CRUD
  API, with its URL written onto the parameter node — clean for consumers, but resurrects the
  `/state/{name}` surface ADR 0015 retired and leaves two parallel REST surfaces to keep consistent.
- **Fixing recursion upstream in `aas_middleware_inf`** — every consumer would benefit, but it is a
  feature in a sibling repo, which the dependency policy forbids without amendment.

## Consequences

- The route path is **structural**: it mirrors the datamodel tree, so a consumer that has GET-ed a
  resource can derive every parameter's URL from the response without knowing a naming convention.
  This is why the controller needs no per-parameter endpoint triples (ADR 0018).
- The local router must track `aas_middleware`'s generator as it changes, until that layer is fully
  reimplemented locally. That is now specifically the **top-level CRUD**, which the router calls
  rather than owns. Everything below the root is ours.
- **Open item:** ADR 0015's write-back rule persists exposure metadata per parameter. With structural
  paths, no consumer needs a per-parameter endpoint triple. Whether registration still writes one is
  left to the consolidation capstone #39's write-back scope — deferred, not dropped.
- Path segments remain IRI-derived and mangled (`prop_iri.lined`), which ADR 0005's #13 amendment
  already flags as unwieldy. Recursion does not make that worse and does not fix it.
