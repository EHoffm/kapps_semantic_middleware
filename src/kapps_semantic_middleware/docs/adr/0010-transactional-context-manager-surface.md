# The programmatic surface is transaction context managers

The way domain Python code drives the middleware is a family of **context managers**. This excludes REST callers. Each context manager is one transaction. The pattern is: preconditions checked in `__enter__` *outside* the transaction. The domain's own code runs in the body. The atomic commit happens in `__exit__` on clean exit. The commit **reverts and re-raises on exception**. Every **write-bearing** entrypoint takes this shape. Examples: `handover` (possession switch), `claim_next` (pull-and-run of a queued Operation), and `request` (caller-side dispatch: create the Operation and fire the receiver's event trigger). Pure **reads** (`fetch`, `resolve`, state GET) stay immediate method calls. There is no transaction to guard.

**Why**: this directly operationalizes the project's standing constraint. The constraint is this: *every graph write is a transaction. Precondition checks happen before it. A failed transaction reverts.* This operationalization uses the actual API shape. It does not leave the constraint as a discipline each call site must remember. It is also the pattern the two systems this team already knows converge on. SQLAlchemy's unit of work is `with session.begin(): ...`. It flushes and commits on clean exit. It rolls back on exception. This is *exactly* the handover context manager (#7) generalized. Kadi-APY (the RDM platform in the same research cluster) uses `with KadiManager() as manager:` for session **lifecycle**. It uses immediate per-call writes for everything else. Reads stay plain. The middleware's own lifecycle (start/register→deregister/stop) stays plain. Only the guarded units of work become `with`-blocks. Considered and rejected: (a) CM only for handover, which leaves pull-and-run to set status and dump state by hand. This loses the automatic, uniform revert-on-failure. A physical body can raise. This is exactly where revert-on-failure matters. (b) every call a CM including reads. This is ceremony with no transaction to protect.

**Consequence**: `execute()` (the receiver-side event trigger) and the REST endpoints are *not* part of this surface. They are the wire/REST face (ADR 0009, ADR 0005). The context managers are the in-process face for the domain code co-located with a resource. The handover core still never references `execute()` (#7). Its body is domain-owned. The body may itself open a `request(...)` dispatch to drive a counterpart. New write-bearing middleware capabilities are expected to arrive as context managers of this same shape. All commits inside `__exit__` still go through the OGM's atomic `DELETE/INSERT` write-path (ADR 0008). The cardinality-constrained possession switch is never transiently invalid.
