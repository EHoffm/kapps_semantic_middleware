# Heartbeat on resource-mode services, sweeper as watchdog mode

Every resource-mode `SemanticMiddleware` runs an internal periodic Workflow. The Workflow uses `aas_middleware`'s existing interval-workflow support (`interval=..., on_startup=True`). The Workflow refreshes an `svc:lastHeartbeat` timestamp on its own Service individual. Separately, `mode="watchdog"` instances run a sweep loop. The loop queries for Service individuals. The query finds Service individuals whose `svc:lastHeartbeat` went stale. The loop deregisters those individuals. Deregistration removes `svc:address` and their Workflows'/StateProperties' `svc:endpoint`. The removal logic matches graceful shutdown.

**Why**: graceful-shutdown-only deregistration leaves the graph permanently pointing at dead processes. This occurs after any crash, kill, or power loss. This is a standard "stale service registry entry" failure mode. The paper names this failure mode explicitly. The paper lists it as a known limitation of the architecture as evaluated. The paper states "middleware-level heartbeat supervision, complemented by a triple store-side watchdog that removes stale discovery triples when a resource-bound middleware instance falls silent". The paper's phrasing splits this into two responsibilities. The responsibilities are per-instance heartbeat and centralized sweeping. This split is why it became a third `mode` rather than a flag on resource mode. A sweeper has no resource to wrap. Unlike resource or server mode, a sweeper does not answer requests at all. A sweeper is the one process type whose entire job is background maintenance of the registry.

**Consequence**: a real deployment needs at least one running `watchdog`-mode instance. The "no dangling registrations" guarantee holds in practice only with this instance. The guarantee is not automatic just because heartbeat code exists. Heartbeat interval and staleness threshold are runtime parameters. They are not architectural choices. These parameters need tuning. Tuning occurs once this runs against a real fleet of concurrent instances. This session used a two-scenario demonstration. The real fleet differs from that demonstration.
