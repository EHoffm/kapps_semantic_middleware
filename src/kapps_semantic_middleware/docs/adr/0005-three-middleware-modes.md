# Three middleware modes: resource, server, watchdog

`SemanticMiddleware` takes a `mode` constructor parameter with three values:

- `"resource"` (built first): wraps one `resource_iri`. User-registered `@workflow`/`@state` functions are the REST-facing surface. Built-in functionality (`execute`, CRUD via the OGM) is exposed only as plain Python methods. It is not exposed as REST routes.
- `"server"` (not yet implemented): wraps no resource. `execute`/CRUD *are* the REST surface. For example, a future "product server" answers `fetch`/`ClassScope` requests against the graph for other services. Its entire purpose is to answer these requests.
- `"watchdog"` (built alongside resource mode): wraps no resource. It exposes little to no REST surface. It instead runs a sweep loop. The loop deregisters Service individuals whose heartbeat has gone stale. It removes `address`/`endpoint` from them.

**Why**: these three shapes were each raised independently during design. A bare hello-world function. A future data-serving service with no physical resource. A liveness-sweeping process with no resource *and* no meaningful REST surface. These turned out not to be variations on one shape. They are three genuinely different answers to "what is this middleware instance for?" Do not let that surface as three unrelated classes. Do not let it surface as three sets of ad hoc constructor flags. `mode` makes the distinction explicit and exhaustive at construction time. `execute`/CRUD exist as Python-only methods in resource mode. They are the REST surface in server mode. This follows directly from what each mode's purpose actually is. In resource mode, workflows are the point. `execute` acts as plumbing. A resource-mode instance uses it internally. For example, it triggers *other* resources' capabilities. In server mode, there are no workflows. `execute`/CRUD have nothing to hide behind.

**Consequence**: `server` and `watchdog`-as-a-concept both existed as scope only at design time. Pull `watchdog`'s sweep logic into this session's build scope alongside resource mode. See `src/kapps_semantic_middleware/docs/adr/0007-heartbeat-and-watchdog-mode.md` for details. Its two-part decomposition (heartbeat + sweeper) became clear. `server` mode remains a documented, reserved mode value with no implementation yet.

**Amendment (2026-07-17, event trigger model).** This ADR said `execute` is exposed *only* as a plain Python method in resource mode. That is no longer true for `execute()` itself. Under the event trigger model (ADR 0009) `execute()` is the receiver-side intake. Expose it as a **built-in Workflow on the REST API**. A caller on another host can trigger it. The corrected resource-mode REST surface is therefore: user-registered Workflows/StateProperties **plus the built-in `execute()` event trigger**. Everything else stays Python-only. CRUD is Python-only. The transactional context-manager surface is Python-only (dispatch/`request`, pull-and-run, handover, ADR 0010). None of these is REST-exposed in resource mode.

**Amendment (2026-07-17, #13 — resource datamodel REST interface).** Resource mode now *also* stands up a **CRUD REST API generated from the resource's own datamodel**. On startup the middleware OGM-fetches the resource individual. It materializes its `aas_middleware` datamodel. It calls `generate_rest_api_for_data_model` (the `generate_rest_interface` path). This **relaxes the "CRUD stays Python-only" stance** of the previous amendment. The *resource's own datamodel* is REST-exposed. Peers can read/observe it. What remains Python-only is the transactional context-manager surface (`request`/dispatch, pull-and-run, handover, ADR 0010) and the graph-write helpers. Never REST-expose these in resource mode. The generation is best-effort. Skip a resource with no materializable data. Do not treat it as fatal. Derive the generated route path verbatim from the resource IRI. This is unwieldy. Plan a cosmetic follow-up for #14.

**Amendment (2026-07-27, #32 — a controller is a resource-mode planner, and `server` stays reserved).** Scenario3's controller discovers TransferUnits through the graph. It drives them over REST. It was the first real candidate for `server` mode. It does not fit. This ADR defines `server` as a *graph-serving* shape. "`execute`/CRUD *are* the REST surface … answering `fetch`/`ClassScope` requests **for other services**". A controller is the mirror image. It *consumes* the graph. It calls *other* resources' endpoints. Nothing calls it inbound. Nor in the v1.1 bootstrap, #35, which is outbound too. Adopting `server` mode here would have meant redefining it. Do not implement it. So the controller is a **resource-mode planner**. Use its own `cfc:Resource` and `svc:Service` class. Use exactly the same class as scenario1's planner and scenario2's mobile robot. `server` mode remains reserved and unimplemented. Record it as Out of scope on map #24.

The scenario is a learning vehicle. It surfaced a real defect in how that pattern was used. Scenario1's planner and scenario2's robot are *constructed* in resource mode. They are **never served**. `on_start_up` never fires. They never register. They exist only to hold an `ogm`. "Resource mode" was a label with no runtime consequence. The controller is served for real. It registers. It heartbeats. It appears in its own discovery list as a resource with no controllable parameters. Retrofit scenarios 1 and 2 to match. All three examples show one consistent pattern.

Resource mode is also the shape the library is *shipped* in. Weave it into domain code as a Python library. Do not run it as a standalone server. The view it exposes is a constructor parameter (ADR 0018). The embedding code knows what the instance is for.
