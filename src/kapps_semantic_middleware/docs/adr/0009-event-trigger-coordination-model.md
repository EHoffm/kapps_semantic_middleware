# Inter-service coordination is an event trigger over a graph-backed operation queue

Services coordinate by **passing Operations through the graph and firing an event trigger**. Services do not coordinate by synchronous RPC. The caller **dispatches**. The caller creates the Operation individual in the graph. The creation uses the OGM write path. The Operation is addressed to a target Resource through its Capability. The caller then **triggers the receiver's `execute()`**. `execute()` is a built-in Workflow every resource-mode middleware exposes on its REST API. The trigger carries only the Operation IRI. The payload lives in the graph. `execute()` **enqueues** the Operation. `execute()` calls `ogm.fetch`. `execute()` hands the Operation to an optional domain callback. `execute()` leaves the Operation `queued` if no callback exists. `execute()` returns immediately. `execute()` does not block on the work. `execute()` does not return a business result. The receiving domain later **pulls** the next Operation. The domain runs the Operation. The domain records the outcome. This replaces the previous synchronous `execute()`. The previous `execute()` resolved an endpoint. The previous `execute()` blocked on an `httpx` POST to the workflow. See the amendment to ADR 0005 and the annotation on ADR 0002.

**Queue durability.** The Operation and its status are written to the graph *before* the trigger. The graph is the source of truth. The per-resource queue is an in-memory cache. On startup a middleware reconstructs its queue. The middleware queries the graph for its own `queued` Operations. The middleware reclaims its own orphaned `running` ones. A missed trigger loses no work. The receiver may be briefly down. A restart loses no work. The event trigger is a latency optimization. The baseline is self-healing. A `watchdog`-mode instance centrally sweeps a *dead* resource's stranded Operations. Resources do not poll (ADR 0007). This design was chosen over a continuous per-resource poll. ~20 resources against one graph should not each poll. This design was chosen over a purely in-memory queue. An in-memory queue silently drops work on restart.

**Status lifecycle.** An Operation moves `queued → running → done | failed`. Execution provenance is written **as part of the terminal transition**. The provenance records which Workflow ran the Operation. The provenance records when the Workflow ran the Operation. The provenance records the result. The status *is* the provenance record. The old separate `svc:executionSuccess` boolean is dropped. `done` vs `failed` already carries this information. See ADR 0010 for the pull-and-run context manager that owns these transitions. See ADR 0012 for where the status vocabulary lives (`svc:`, as middleware coordination).

**Recovery is never a silent physical replay.** An orphaned `running` Operation transitions to `failed`. The resource crashed mid-execution. The middleware finds the Operation at startup-pull or by the watchdog. The failed status carries any dumped resource state. The planner/domain decides whether to dispatch a fresh Operation. Physical operations are frequently not safely repeatable. Examples: a half-driven screw, a mid-transport. Recovery is explicit. Recovery is never an automatic re-actuation.

**Consequence.** The event/push-notification primitive (R8 — the sender being notified when an Operation reaches a status) is **not** required. It stays deferred (per #4). The model is poll/queue-based. The scenarios and use cases serve as learning vehicles for this model. They are not fixed production contracts. Building them may expose friction in how the built-in (non-domain) workflows are shaped. The coordination internals here are the thing to rethink. The scenario is not the thing to rethink.
