# All knowledge-graph writes go through the OGM

Every knowledge-graph **write** in this project goes through `kapps_ogm.OGM`. Use `OGM.create` for new typed individuals. Use `OGM.commit` for adding, removing, or replacing properties. No write issues raw SPARQL UPDATE. No write calls the `graph_db_interface` mutation methods directly. **Reads** may use the access module (`ogm.db`) directly. The architecture permits reads there. Only writes are constrained.

**Why**: the paper's central architectural commitment states "every write originates as an OGM commit... making the OGM the architecture's single validated write path" (§4.4.2). An earlier iteration of this project violated that commitment. `registration.py` wrote structural triples directly via `graph_db_interface`. The code used `triples_add`, `triple_add`, and SPARQL `DELETE WHERE`. The `KnowledgeGraphConnector` (ADR 0006) was never wired in. No write went through the OGM at all. That was a fidelity shortcut. This document corrects that shortcut.

Realizing this commitment required fixing three latent defects in `kapps_ogm`'s commit path. The defects were a `datetime` serialization crash, `from_node_data` dropping empty-valued keys so removal was impossible, and `commit` requiring equal-length diffs. Realizing this commitment also required generalizing `graph_db_interface.triples_update` to a single `DELETE/INSERT` transaction. The atomicity is not incidental. A replacement of a cardinality-constrained property must apply the removal and the insertion in one transaction. Example: a possession handover under a "possessed by exactly one resource" SHACL shape. The intermediate (zero-possessor) state fails validation without atomicity.

**Consequence — one direction of each inverse is materialized.** `OGM.create` writes a single instance's own properties. Appending to a multi-valued property would require a read-modify-write. Example: a Service's `svc:hasWorkflow` as each workflow registers. We materialize only the direction owned by the newly-created instance. We materialize a Service's `svc:isServiceOf`. We materialize a Workflow's `svc:isWorkflowOf` and `svc:endpoint`. We materialize a Capability's `svc:realizedByWorkflow`. We materialize a StateProperty's `svc:isStatePropertyOf`. The container-side inverses (`svc:hasWorkflow`, `svc:hasService`, `cfc:hasCapability`, …) are OWL-inferable. The container-side inverses are not written. Queries in this project use the materialized (instance-owned) direction. `resolve` follows `svc:realizedByWorkflow`. `deregister` finds a service's workflows via `svc:isWorkflowOf`. A deployment with OWL reasoning enabled recovers the inverses automatically. A reasoning-free store has one direction. One direction is sufficient for this project's own read paths. `cfc:hasCapability` (Resource→Capability, no inverse in Core, multi-valued) is not materialized in v1. It is not on any read path here. Adding it would be the one place needing an append. Adding it is deferred.

**Amendment (2026-07-21, #17 — Resource→Capability is now materialized).** The deferral above is lifted for `cfc:hasCapability`. Queue durability (ADR 0009) requires a resource to find its own Operations by **ontology traversal**. The traversal is `?op cfc:implementsCapability ?cap . <resource> cfc:hasCapability ?cap`. The traversal does not match IRI names. `register_workflow` / `register_state_property` now write `cfc:hasCapability` (Resource→Capability) as each Capability registers. This is the first container-side inverse this project materializes. It is written on the pre-existing resource. The only available direction is this direction. Core gives `hasCapability` no inverse. It is now on a read path. The read paths are `find_resource_operations` and the watchdog sweep. The "queries use the materialized instance-owned direction" invariant is relaxed. Queries traverse whichever ontology link the read needs. This project materializes the links its reads traverse. This project never identifies entities by IRI name.

**Mechanism note.** `cfc:hasCapability` is a **Core** term. `cfc:implementsCapability` is a **Core** term. An Operation's `rdf:type` in `create_operation`/`revert_operation` is a **Core** term. The property domains for these terms are not declared in the Core *subset* the scenarios load. `OGM.create`/`commit` cannot hydrate these terms. These terms are written through the low-level API of `graph_db_interface`. This is a bounded, documented exception to the OGM-only write rule. The loaded-subset limitation forces this exception. Routing these Core writes through the OGM requires the loaded ontology to declare property domains for `cfc:Operation` and `cfc:Capability`. This is a `kapps_ogm`/ontology follow-up. See the `create_operation` docstring.

**Amendment (2026-07-22, follow-up — `create_operation` now writes through `OGM.create`).** Re-checked against the paper (the reference implementation's ground truth). Section 4.3 states that every write originates as an OGM commit. This makes the OGM the architecture's **single validated write path**. Section 4.4.2 places that validation at the Python boundary, before the code builds any SPARQL update. The raw-triple writes above are a **fidelity gap**. They are not a blessed alternative path. The `graph_db_interface` is not a service-facing write path. This amendment closes that gap for **Operation creation**. The loaded scenario/demo ontologies now declare `cfc:implementsCapability` (`rdfs:domain cfc:Operation`, `rdfs:range cfc:Capability`). `create_operation` persists the whole Operation (`rdf:type` + `implementsCapability` + `svc:operationStatus`) in one `OGM.create`.

**What is *not* yet closed, and why.** Two low-level writes remain. Each remains for a principled reason:

- `cfc:hasCapability` (written at registration, Resource→Capability) is **multi-valued**. A resource provides many capabilities. `OGM.commit` has whole-property-set *replace* semantics. Routing an append through it would clobber the resource's other capabilities. The correct fix is a **validated single-triple append in `kapps_ogm`**. The paper, §4.4.2, explicitly envisions the OGM adding/removing individual property assertions. Per ADR 0001 that is a `kapps_ogm` enhancement. That is not an ad-hoc addition here. This is the **same** gap as `cfc:hasPossessor` in `switch_possession`/`create_possession` (ADR 0011). Both are multi-valued appends parked on `ogm.db.triple_add`. Both await that one capability.
- `revert_operation`/deregister **deletions** stay on `ogm.db.triple_delete`. The OGM intentionally offers no entity deletion (paper §4.4.2). Triple-level removal is the sanctioned access-module operation for "remove exactly what was written."
